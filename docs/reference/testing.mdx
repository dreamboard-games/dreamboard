title: "Testing"
description: "Verify game rules using TypeScript and Vitest."
---

Keep rule tests in the game project and run them with `pnpm check`. Use the SDK's testing helpers to initialize a game, submit player inputs, and assert resulting projections. Test accepted actions, rejected actions, hidden information, setup seeds, and terminal outcomes.

The local browser host exercises the same five-member reducer bundle (`initialize`, `dispatch`, `project`, `boardStatic`, and `reducerContractVersion`). `pnpm dev` lets you switch seats and reset a session while inspecting the authored UI.

Repository browser tests also prove operation serialization, persistence before publication, resume, reset, worker timeout termination, fresh module isolation, and denial of worker storage/network access. These checks are separate from a game's rule tests.

## Recommended coverage

Author scenarios from normal setup for:

- opening projections and action availability
- representative turns, rounds, prompts, or response windows
- important rule branches and complete game outcomes
- player-count and seat-order differences
- deterministic seeded behavior
- typed rejection probes such as wrong actor, insufficient resources, stale
  input, or action after game end

Use pure unit tests for isolated algorithms such as scoring or graph
connectivity. Use scenarios for reducer integration. Do not hydrate state or
introduce a test-only setup path to shorten a game arc.
