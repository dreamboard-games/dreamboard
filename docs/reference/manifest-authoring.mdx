---
title: "Manifest authoring"
description: "One authored manifest defines component identities and board topology."
---

Import `defineTopologyManifest` and `compileManifest` from `@dreamboard-games/sdk/reducer`. Keep the manifest in an ordinary `manifest.ts` module:

```ts
import { defineTopologyManifest } from "@dreamboard-games/sdk/reducer";
export default defineTopologyManifest({
  players: { minPlayers: 2, maxPlayers: 4 },
  cardSets: [],
  zones: [],
  boards: [],
});
```

The game model accepts this manifest directly. `compileManifest(manifest)` exposes inferred ID schemas, a table schema, static board data, and `createInitialTable({ playerIds })` for host initialization. Do not maintain generated contracts, a second manifest parser, or handwritten identity unions.

Author boards inline in `boards`. Use `layout: "hex"`, `"square"`, or `"generic"` and declare stable spaces and their fields. Hex edges and vertices derive from the authored topology. Per-player boards expand for the actual roster; player-board targets retain both board and player identity.

Zones describe component membership and canonical visibility. `scope: "shared"` creates one table-wide container; `scope: "perPlayer"` creates one container for each player. A hidden zone is not an invitation to send its card identities to the UI. The canonical projection and the authored seat view determine visibility.

Manual card counts expand into runtime card IDs. Piece and die seeds create their component instances. Preset card sets such as `standard_52_deck` are materialized by the SDK. Keep artwork and semantic labels in component data, and keep rendering layout in the UI.

Initialization options belong to the game model's validation-only Zod `options` schema, not manifest setup options or profiles. Perform deal, shuffle, and resource mutations explicitly through transactions in a phase entry callback. All gameplay randomness uses the initialized seeded RNG.
